## 03:21:52 UTC · collector-error · SandboxCommandTimeout

collect.py cannot finish a solana pass inside one dispatch-sandbox command

```
Not a fault in collect.py. An environment limit that will silently zero out every scheduled hour if left alone.

The dispatch sandbox caps a single shell command at ~178s. A full pass needs longer:
  scanner.scan + journal.record       ~150s (5 pages of new_pools, then Dexscreener enrichment paced at 0.25s over ~80 pools)
  track.score_all                     ~160s (up to 80 pairs per horizon x 4 horizons, each a paced HTTP call)
  total                               ~5 minutes

First attempt: 'python3 collect.py solana' was killed at 178s partway through the scan. Nothing journalled, no traceback, no non-zero exit visible to the caller. The NOTHING JOURNALLED guard in collect.main never ran because main() was killed before reaching it.

Backgrounding does not work around it. The sandbox runs each command under 'bwrap --die-with-parent', so a setsid/nohup child is killed when the command returns. A background run appeared alive only because 'pgrep -f collect.py' was matching the polling command's own cmdline. Confirmed dead: /tmp/collect_run.log stopped at the pass header and never advanced.

Workaround used for this pass, which completed the full pass correctly:
  1. scanner.scan + journal.record + record_coverage + notify   (one command)
  2. track.score_horizon(1)                                     (one command)
  3. track.score_horizon(6)                                     (one command)
  4. track.score_horizon(24)                                    (one command)
  5. track.score_horizon(168)                                   (one command)
Journal is append-only and outcome scoring is idempotent, so the split is behaviour-identical to one_pass().

Durable fix would be either a --stage flag on collect.py so the scheduler can drive it in pieces, or a resumable pass that checkpoints and exits under the cap.
```
